## Project overview

"Magia Cristais" — a Nuxt 4 site cataloging minerals/crystals, including their physical properties (Mohs hardness, colors) and mystical/crystal-healing properties (element, planet, zodiac signs, chakras, magical properties). Public catalog + an admin dashboard for CRUD management. Content and UI are in Portuguese (pt-BR).

## Commands

```bash
npm run dev          # dev server on http://localhost:3022 (port set in nuxt.config.ts)
npm run build         # production build
npm run generate      # static generation
npm run preview       # preview production build
```

There is no lint script and no test suite configured in this repo. Use `npx nuxi typecheck` for TypeScript checking (project references live in `.nuxt/tsconfig.*.json`, generated by `nuxt prepare`/`postinstall`).

## Architecture

### Data layer: two Firestore access paths

Firebase is initialized twice, for different runtime contexts:

- **Client**: `app/plugins/firebase.client.ts` initializes the Firebase app and provides `$auth`/`$db` via `useNuxtApp()`. Only available in the browser (`.client.ts` suffix + `import.meta.server` checks). Used for all admin write operations and for auth state.
- **Server**: `server/utils/firestore.ts` (`useServerFirestore()`) initializes a separate named Firebase app instance for use inside Nitro API routes (`server/api/**`). Used for public, read-only, cacheable data fetching (home page, mineral detail, search, about page). These routes set `cache-control` headers with `s-maxage`/`stale-while-revalidate` for CDN caching.

Public pages fetch data through `server/api/*` endpoints via `$fetch`/`useFetch`. Admin pages read/write Firestore directly from the client through the composable stores below (no server API layer for admin CRUD).

### Client-side stores: singleton composables, not Pinia

`app/composables/useMineralsStore.ts`, `useCategoriesStore.ts`, `useAboutContent.ts`, and `useFeaturedMineral.ts` all follow the same pattern: `ref()` state declared at module scope (outside the exported function) acts as a shared singleton store across all consumers, with no Pinia/state library involved. Each composable's `onMounted` hook lazily triggers an initial fetch exactly once (guarded by an `initialized` flag), specifically to avoid running Firestore queries during SSR (no `$db` on the server) and to avoid hydration mismatches (SSR always renders the empty/loading state). When adding a new collection-backed store, follow this same shape rather than introducing a different state pattern.

### Auth

`app/middleware/auth.global.ts` is a global route middleware that only acts on `/admin/**` and `/login`, and only runs client-side (`import.meta.server` early return, since Firebase Auth isn't available during SSR). It waits on the first `onAuthStateChanged` callback before deciding to redirect, so auth state on first load is resolved before route access is granted/denied.

### AI-assisted mineral data entry

Two Nitro endpoints call the Groq API (`llama-3.3-70b-versatile`, JSON mode) using a server-only `groqApiKey` (never exposed to the client):

- `POST /api/structure-mineral` — takes free-form text and the list of existing categories, returns a fully structured mineral record.
- `POST /api/improve-mineral` — takes an already-structured mineral and asks the model to copy-edit the free-text fields (`description`, `magicalProperties`) and only correct structured fields (hardness, colors, element, planet, zodiac signs, chakras) when clearly wrong — not restyle them.

Both endpoints share the same fixed vocabularies (`COLOR_PALETTE`, `ELEMENTS`, `PLANETS`, `ZODIAC_SIGNS`, `CHAKRAS`) duplicated in each file, and both defensively re-validate every field the model returns against those vocabularies before responding, falling back to the caller's original value on anything invalid/missing. Keep the vocab lists in sync between the two files if either changes. The client-side `app/composables/useMineralAI.ts` wraps both endpoints and mirrors their TypeScript interfaces.

### Images

Uploads go straight from the browser to Cloudinary's unsigned upload API (`app/composables/useCloudinaryUpload.ts`), not through a server route. Display uses `@nuxt/image` with the `cloudinary` provider (configured in `nuxt.config.ts` with `NUXT_PUBLIC_CLOUDINARY_CLOUD_NAME`).

### UI components

Built on `shadcn-vue` (`reka-nova` style, prefix-less) — components live in `app/components/ui/**` and are regenerated/added via the `shadcn-vue` CLI (see `components.json` for aliases: `@/components`, `@/lib`, `@/composables`, etc.), not hand-written from scratch. Icons come from `@lucide/vue` via `nuxt-lucide-icons` (auto-imported as `Lucide<Name>`). Feature-level components (`MineralCard`, `MineralForm`, `RichTextEditor`, `ThemeToggle`) live directly in `app/components`.

Two layouts: `default` (public site — header/nav/footer) and `admin` (sidebar dashboard, set via `definePageMeta({ layout: 'admin' })` on admin pages). Dark mode uses `@nuxtjs/color-mode` with class-based toggling (`classSuffix: ''`, i.e. `.dark`), default preference `light`.

Typography uses custom Tailwind v4 `@theme` tokens defined in `app/assets/css/tailwind.css` (e.g. `text-hero`, `text-section-title`, `text-card-name`, `text-body`, `text-eyebrow`, `font-heading` for the Dosis display font) rather than default Tailwind text sizes — prefer these tokens over ad hoc `text-*`/`font-*` utilities when styling new UI to stay consistent with the rest of the site.
